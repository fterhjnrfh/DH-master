# 当前实时曲线主要矛盾分析

更新时间：2026-04-21

## 目标

先不讨论包络线、异常值保真这条线。

当前先解决的核心问题是：

- 单视图 `1V-64C` 要稳定高帧率
- 多视图尤其 `64V-16C`、`64V-64C` 要显著提升
- 不改原有结果页结构和单视图显示语义

也就是说，当前阶段的主要矛盾不是“点语义是否最理想”，而是：

**现有实时绘制链路没有把多视图场景下的重复计算和串行渲染成本压下去。**

---

## 现状结论

根据近期多轮测试数据，当前表现大致稳定在：

- `1V-64C`：大多在 `49~54 FPS`
- `64V-16C`：明显低于目标
- `64V-64C`：仍然只有个位数 FPS

这说明：

1. 单视图链路已经不算完全失败，基础路径能跑起来。
2. 多视图场景仍然存在结构性瓶颈。
3. 继续围绕“上游小缓存”“空帧短路”“轻微数据流微调”反复打补丁，收益已经很有限。

---

## 当前真实链路

结果页当前的实时绘制链路是：

1. `MainWindow` 固定 `5ms` 刷新一次所有 `CurvePanel`
2. 每个 `CurvePanel` 在需要时构建当前 sweep 窗口数据
3. `SkiaMultiChannelView` 对每个 panel 单独执行一次 `RenderSkia()`
4. `RenderMulti()` 内部再做：
   - 通道遍历
   - `maxCount` 统计
   - 有序通道列表构建
   - X 范围推断
   - Y 范围估计/锁定
   - bin 聚合
   - 坐标投影
   - 逐通道逐段绘制

当前已经有的优化包括：

- `RealtimeDisplayCache`
- `RealtimeSweepSnapshotCache`
- `CurvePanel` 层窗口缓存
- `SkiaMultiChannelView` 的部分缓冲复用
- 背景层/坐标轴层缓存

这些优化都不是没价值，但它们没有打到当前最重的主矛盾。

---

## 主要矛盾到底是什么

当前最重的成本，不在“有没有少调一次 provider”，而在下面这两层：

### 1. 多视图下的重复渲染前处理

虽然 `CurvePanel` 已经能共享部分窗口快照，但一旦进入 `SkiaMultiChannelView.RenderMulti()`，每个 panel 仍然要重新做：

- 遍历通道集合
- 重新统计 `maxCount`
- 建立 `ordered` 列表
- 重新判断绘制策略
- 重做 bin 划分
- 重做点到像素的投影

这部分在单视图下还能接受，但在 `64` 个视图同时存在时会被放大。

### 2. 渲染工作高度串行，吃不满 CPU / GPU

当前工作负载的特点是：

- UI 主线程驱动
- 每 `5ms` 全量刷新
- 每个 panel 各自进入 Avalonia/Skia 绘制
- 大量小对象、小循环、小段绘制

所以当前不是“机器性能不够”，而是：

- CPU 不能高效并行
- GPU 也没有被喂成大批量任务
- 结果表现为总利用率不高，但 FPS 上不去

---

## 已经验证过的结论

下面这些方向已经做过，或者至少被近期测试证明不是主矛盾：

### 1. 只做上游数据缓存，不足以解决多视图

已有：

- `RealtimeDisplayCache`
- `RealtimeSweepSnapshotCache`
- 最新时间戳缓存
- 窗口最大振幅前移

结论：

- 这些能减少部分 `CurvePanel` 重复准备数据的成本
- 但不能把 `64V-64C` 从个位数 FPS 拉到目标区间

原因：

- 真正重的部分还在 renderer 内部

### 2. 激进的“空帧短路”很容易伤单视图

近期已经出现过：

- 多视图没明显变快
- 单视图反而出现明显卡顿

结论：

- 当前不应继续优先碰“过于激进的复用短路”
- 尤其不要先动单视图稳定路径

### 3. 继续微调小分配，收益有限

像下面这些：

- 少 new 一些临时容器
- 少拷一次字典
- 少扫一次时间戳

都有价值，但已经不再是决定性矛盾。

---

## 当前不该优先解决的事

下面这些不是当前阶段第一优先级：

### 1. 包络线 / 异常值保真

这件事很重要，而且后面必须做。

但它是“正确性与信号保真”问题，不是当前多视图性能的第一主矛盾。

如果现在先大改这一层，容易把问题混在一起，导致：

- 性能瓶颈没拆清楚
- 信号语义又一起变了
- 更难定位问题

### 2. 历史回放逻辑

当前只看实时绘制。
历史归档、回放、历史包络不作为当前主线。

### 3. 单宿主大重构

从纯性能角度看，“单宿主多 panel”仍然是一个强方向。

但当前用户约束是：

- 不优先改结果页原有结构
- 先把现有结构下的主矛盾分析清楚

所以当前阶段先不把它作为立即落地项。

---

## 当前阶段最值得做的优化方向

### 方向 1：冻结单视图稳定路径

原则：

- 不碰单视图 sweep 语义
- 不碰刷新机制
- 不碰会明显影响 `1V-64C` 流畅度的激进短路

目标：

- 先保护住现在单视图基本可用的结果

### 方向 2：只针对多视图密集模式做渲染前处理缓存

重点在 `SkiaMultiChannelView.RenderMulti()` 内部。

优先做：

- 缓存 `ordered channel ids`
- 缓存 `maxCount`
- 复用通道画笔对象
- 缓存绘制策略判断结果

原则：

- 只在多视图密集模式启用
- 不改变当前显示语义
- 不影响单视图路径

### 方向 3：把“渲染前处理结果”从 renderer 内部提出来

当前共享缓存止步于 `CurvePoint[]`。

下一层更应该缓存的是：

- 已排序通道列表
- 当前窗口的可见范围统计
- 每通道 bin 结果
- 每通道投影前的代表点序列

也就是说，不只是缓存“数据”，而是开始缓存“接近可直接绘制的中间结果”。

这是现阶段最有希望继续提升多视图的点。

### 方向 4：关闭热路径里的诊断和非必要检查

像振幅溢出诊断、额外日志、每帧调试判断，后续都应该：

- 保留能力
- 但默认关闭
- 仅在排查问题时显式打开

否则它们会持续污染热路径。

---

## 推荐的执行顺序

当前建议按下面顺序推进：

1. 冻结单视图路径，不再做激进短路类改动
2. 只对 `attachedViewCount >= 16/64` 的多视图密集模式做专门优化
3. 在 `RenderMulti()` 内先做低风险缓存：
   - `ordered`
   - `maxCount`
   - `SKPaint`
   - 绘制策略
4. 再做“渲染预处理缓存”，把 bin / 投影前结果前移
5. 最后再回头处理包络线与异常值保真

---

## 一句话总结

当前阶段的主要矛盾不是“信号语义是否最优”，而是：

**多视图下，大量重复的渲染前处理仍然留在每个 `SkiaMultiChannelView.RenderMulti()` 里串行执行，导致 CPU 和 GPU 都没有被有效利用。**

因此，下一阶段优化主线应该是：

**冻结单视图稳定路径，只针对多视图密集模式，把 renderer 内部的重复准备工作继续拆出去做缓存。**
